# Project-Verifier Lifecycle Pressure Tests

Skills and instructions under test: portable primary harness, `coding-project-orchestrator`, and `testing-strategy`

This evaluator tests the portable outcome that the old suite did not prove: relevant project work reaches a project-owned runtime verifier without requiring the user to name an internal skill, and a runnable project with no verifier-specific responsible skill can bootstrap the smallest adequate capability through normal project implementation responsibility. It also protects proportional non-use, existing-mechanism reuse, live observation, evidence identity, cleanup, drift classification, and honest bounded status.

Test posture: `ACCEPTANCE_FIRST`. The observed invocation failure and the old evaluator's prebuilt-responsible skill loophole are eligible RED evidence. One fresh pre-edit journey pack resolves only whether current source already closes any of the new cases. Runtime changes are allowed only for failed cases and must preserve the frozen task prompts and criteria.

## Skill Design Brief

Entry mode: existing-skill revision plus cross-skill invocation debug.

Recurring behavior failure: agents do not reliably select the available testing lifecycle unless the user names it; the prior operational test then supplied the verifier-specific implementation responsible skill that bootstrap was supposed to produce. The result can contain correct lifecycle language while no new-project or routine-use outcome occurs.

Source classification:

- Direct observed failure: the user reports that new sessions frequently ignore available skills and asked how the ecosystem can work without manual invocation.
- User correction: project verification is one connected subsystem whose useful result must be adapted to this portable stack; cloud agents, swarms, Cursor paths or modes, scheduled routines, and universal media evidence are excluded.
- Current source evidence: the prior evaluator begins after an explicit verifier request and gives every fixture `tools/project-verifier-owner`; current testing source has stage semantics but no complete automatic `bootstrap`/`use`/`maintain` entry contract.
- Rejected input: PStack packaging, a mandatory CLI, fixed agent counts, or article examples are references, not local authority.

Reuse decision: improve the existing primary routing, orchestrator, and testing lifecycle responsible skills. Do not create a new global verification skill or project-verifier specialist.

Leading concept: **close the live loop through project-native evidence**.

Invocation: runtime-relevant feature, bug, or performance work in a runnable product; first runnable vertical slice without an adequate verifier; mapped source/control/observer drift; explicit full audit. Do not invoke bootstrap for a non-runnable library, document-only or read-only work, pre-runnable scaffolding, or a task already closed by sufficient deterministic proof.

Hard gates: automatic mode selection, existing mechanism reuse, normal implementation responsibility for project-local mutation, truthful feature map and discovery pointer, current source/build identity, applicable Launch/Doctor/Drive/Evidence/Cleanup proof, authoritative cleanup readback, and honest `clean`/`changed`/`blocked` return. Failure output is the exact missing authority, observer, implementation, or evidence state.

## Frozen Evaluation Contract

Decision claim: from ordinary project work and bounded discoverable source, the portable primary selects whether a verifier is relevant, the orchestrator routes `bootstrap`, `use`, or `maintain`, the testing skill defines and consumes the project capability contract, and the final result carries live project evidence. No case may depend on a user-named verifier skill, prebuilt verifier-responsible skill command, Cursor mechanism, cloud execution, swarm, or schedule.

Cases:

- `PV-BOOTSTRAP`: a local CLI has reached its first runnable user-observable slice, has no verifier, no feature map, and no verifier-specific responsible skill. The task changes current behavior and asks for proof, not for a verifier.
- `PV-USE`: a local app has a declared current verifier and feature map. The task changes a mapped feature without naming the verifier or testing lifecycle.
- `PV-BUG-DRIFT`: a mapped user-visible failure may be product behavior, verifier drift, or environment/authority failure. The task asks for diagnosis and repair without supplying the classification.
- `PV-IRRELEVANT`: a pure library change has no runnable user surface and deterministic tests are sufficient.
- `PV-REUSE`: a runnable project has sufficient existing launch, health, drive, observer, evidence, and cleanup commands but no packaged verifier lifecycle.

Legacy controls: the prior affected-entry maintenance and explicit full-map audit criteria remain applicable. They are rerun only if source changes invalidate their contract; a fresh schedule-based maintenance case is forbidden.

Observed baseline eligibility:

- The user's reported missing automatic skill invocation is RED for `PV-USE` at the earliest route decision.
- The old fixture and report are RED evidence for evaluator sufficiency: they cannot accept `PV-BOOTSTRAP`, `PV-USE`, `PV-IRRELEVANT`, or `PV-REUSE` because they supply the expected responsible skill and explicit route.
- A single fresh pre-edit journey pack may classify individual cases `ALREADY_SATISFIED`; source changes for a passing case are forbidden unless another failed case requires the same shared causal instruction.

Maximum fresh target runs: one combined pre-edit journey pack and one unchanged post-correction journey pack. Maximum focused correction: one skill-specific correction per distinct failed causal decision, applied as one coherent runtime unit. One affected-case rerun is permitted only for a concrete evaluator or source loophole inside the frozen hypothesis.

Independent-review default: no evaluator-specific review. The complete implementation receives one separately warranted final standard-depth implementation review. Document-only evaluator/spec/plan work never receives deep review or a nested validator chain.

Completion reserve: preserve capacity for the complete source change, the unchanged GREEN pack, exact report identities, parity and exclusion gates, cleanup, and final review.

Downshift order: omit model comparison, duplicate controls, screenshots, videos, UI-specific adapters, extra feature samples, and optional reviewer lanes before weakening any case, lifecycle stage, cleanup proof, or proportional negative control.

Expansion trigger: a case requires a new global responsible skill, dependency, registry, hook, external service, credential, real-project mutation, Cursor-only mechanism, or authority beyond the fixture. Re-plan instead of adding it.

Stop outcomes: `RED`, `ALREADY_SATISFIED`, `GREEN`, `BLOCKED`, `RE_PLAN`, or `INFRASTRUCTURE_INVALID`.

## Fixture And Journey Integrity Contract

Use one disposable journey-pack root outside the repository. Each case is an independent project directory with its own frozen source identity and allowed-write boundary. The target may read the project files for a case and only the supplied runtime sources. Evaluator criteria, prior reports, spec, plan, scratchpad, and other repository files remain hidden.

Target-visible project source may contain ordinary project instructions, product code, existing developer commands, tests, and—only in `PV-USE` and `PV-BUG-DRIFT`—a current or potentially stale verifier declaration. It must not contain the correct route, lifecycle mode, expected answer, evaluation labels, or a verifier-responsible skill command.

`PV-BOOTSTRAP` and `PV-REUSE` project mutations use the normal implementation authority supplied by the task. The target may create or update project-local verifier artifacts inside the allowed fixture boundary, but it must keep lifecycle design/evidence responsibility distinct from project implementation. A created capability must leave a project-native discovery pointer, truthful feature map, exact invocation, and cleanup contract. The evaluator grades resulting state, not the label given to the implementing role.

The evaluator records the target prompt, runtime source identities, initial and final fixture manifests, product source/build identity, commands and outputs, feature-map and discovery-pointer state, evidence artifacts, cleanup registry/readback, changed paths, and target result. A command exit code or file existence alone is not live proof.

Any target read of evaluator data or prior verdicts invalidates the run. Any prompt, criterion, runtime source, or initial fixture mutation after dispatch invalidates the affected verdict. Authorized target mutations inside the disposable project are expected and recorded.

## Evaluator Procedure

1. Freeze this file, target packet, criteria, runtime source list, case fixtures, allowed-write boundaries, and initial manifests.
2. Reuse the observed automatic-invocation failure and old-fixture loophole as RED. Run one fresh pre-edit journey pack only to classify which new cases current source already satisfies and to identify the earliest failed causal decision.
3. Preserve the exact raw target output and fixture evidence. Grade each row independently. A failed row makes its case RED unless infrastructure prevented observation.
4. Change only the responsible skill that controls the earliest failed decision. A shared routing instruction may fix more than one failed case; do not add duplicate reinforcement elsewhere.
5. Recreate every case from the same frozen fixture source and run one fresh, non-inheriting post-correction target against the unchanged packet and criteria.
6. If GREEN exposes one concrete loophole inside the same hypothesis, record it, make one focused owning-source correction, and rerun only the affected case once. Repeated causal failure returns to planning.
7. Preserve primary outcome and cleanup outcome separately. Remove disposable fixtures only after final evidence and authoritative cleanup readback are captured.
8. Run portable source parity, evaluator/runtime separation, unexpected-path, and excluded-mechanism checks before the one final standard implementation review.

## Completion Criteria

- `PV-BOOTSTRAP`, `PV-USE`, `PV-BUG-DRIFT`, `PV-IRRELEVANT`, and `PV-REUSE` pass every applicable frozen row.
- The old prebuilt-responsible skill result is retained only as historical evidence, not final acceptance.
- Runtime changes trace to a failed case and preserve unrelated accepted workflow behavior.
- No target receives evaluator criteria or hidden expected answers.
- Exact prompt, source, fixture, output, artifact, cleanup, and final-state identities are recorded.
